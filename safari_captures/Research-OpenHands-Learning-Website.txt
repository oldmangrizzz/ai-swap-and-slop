[L67] What OpenHands is now
[L68] A major finding is that “OpenHands” no longer means one monolithic
[L69] application architecture. Current documentation describes a multi-repository
[L70] system, and older tutorials can describe a materially different generation. That
[L71] distinction is essential to a learning environment because mixing old Local
[L72] GUI/runtime instructions with current Agent Canvas/Agent Server instructions
[L73] can produce incorrect deployment and troubleshooting guidance. [4]

[L75] The active component model
[L76] The current browser-facing application is Agent Canvas. It is the browser client
[L77] and control center for conversations, files, model configuration, backends,
[L78] customization, and automations; it connects to one or more backends rather than
[L80] <PARSED TEXT FOR PAGE: 3 / 17>[L81] itself being the execution sandbox. The current Software Agent SDK defines
[L82] agent behavior, conversations, tools, workspaces, events, and related agent
[L83] mechanisms. Agent Server, housed with the SDK, exposes that execution
[L84] capability to clients through HTTP and WebSocket interfaces. Automation
[L85] Server owns scheduled/event-driven work, while Sandbox Server is a separately
[L86] maintained standalone control plane for sandboxed environments. [4]

[L126] These boundaries are directly reflected in the official architecture
[L127] documentation. A remote backend still presents the Agent Server API to Canvas,
[L128] and Canvas can connect to a service on another machine or container.
[L129] OpenHands Cloud and Enterprise add managed backend/control-plane
[L130] arrangements around this model. [5]

[L132] Active, legacy, hosted, and commercial pieces
[L133] The current documentation explicitly marks the former Docker-based Local GUI
[L134] as legacy/deprecated and directs active browser-client development toward
[L135] Agent Canvas. The CLI remains SDK-powered and is described as feature-
[L136] complete and primarily maintained for stability. The archived legacy repository
[L137] preserves the previous backend/runtime design for historical use rather than
[L138] defining the current system. [6]

[L140] OpenHands Cloud is the managed service. OpenHands Enterprise provides
[L141] commercial self-hosting/managed-deployment features for organizations
[L142] requiring those capabilities. Those are not interchangeable with the open-source
[L143] single-user/local arrangements merely because they share OpenHands
[L144] technology. [6]

[L146] Licensing likewise needs to be taught per repository/component rather than as
[L147] one blanket claim. The current OpenHands/OpenHands and OpenHands/software-
[L148] agent-sdk repositories carry MIT licenses, while the official component
[L149] documentation instructs users to check each repository's own license. [7]

[L151] Self-hosting the application is not self-hosting the model
[L152] A self-hosted Agent Canvas/Agent Server arrangement can still send model
[L153] requests to an external model provider. Current model configuration supports
[L154] direct provider profiles, an OpenHands provider path, local OpenAI-compatible
[L155] model endpoints, LiteLLM proxies, and ACP agents such as Claude Code, Codex,
[L156] or Gemini CLI. A locally hosted model is a distinct architecture choice; for local
[L157] model servers, the endpoint must be reachable from the backend, not merely
[L158] from the learner's browser. [8]

[L160] That yields an important teaching distinction:
[L162] <PARSED TEXT FOR PAGE: 5 / 17>[L163]     “OpenHands is on my VM” answers where the control/execution
[L164]     software runs. It does not, by itself, answer where model inference
[L165]     happens.

[L167] The learning environment therefore tracks “application hosting” and “model
[L168] arrangement” as separate VM-profile inputs instead of collapsing them into a
[L169] single “self-hosted” checkbox.

[L171] From a submitted task to an inspectable result
[L172] The site handoff teaches OpenHands as a causal system rather than a collection of
[L173] menus.

[L175] A useful ordinary-language trace is:

[L177] Person → Canvas → selected backend/conversation → agent/model decision →
[L178] permitted tool action → workspace or external service → observation/event
[L179] → next decision → result and verification.

[L181] Agent Canvas sends work to the active backend; the Agent Server owns
[L182] conversation execution and streams observable events back to clients.
[L183] Workspace choice determines which files and processes the agent can reach,
[L184] while the model and agent profile determine the reasoning/model path and
[L185] available agent configuration. [9]

[L187] What actually changes at each step
[L188] When an OpenHands agent takes a step, the underlying SDK model is not simply
[L189] “the AI writes code.” The agent reasons using an LLM, may choose a tool, receives
[L190] the resulting observation, updates conversation state/events, and either continues
[L191] or reaches a stopping condition. Tools can include terminal operations, file
[L192] operations, connected MCP capabilities, and other configured components; those
[L193] capabilities are constrained by the workspace and available tool catalog rather
[L194] than by the agent's prose alone. [10]

[L196] This matters for judging outcomes. An agent saying that something is finished is
[L197] only a claim. Evidence can include changed files, command output, tests, tool
[L198] observations, repository state, application behavior, or another task-appropriate
[L199] verification result. The first activity in the prototype asks the learner to
[L200] distinguish those concepts immediately rather than treating “agent says done” as
[L201] completion.
[L203] <PARSED TEXT FOR PAGE: 6 / 17>[L204] Models and agent profiles are separate controls
[L205] Current Canvas distinguishes an Agent Profile from an LLM Profile. The Agent
[L206] Profile controls which agent and agent-specific configuration a new conversation
[L207] uses; an OpenHands Agent Profile can reference an LLM Profile, which separately
[L208] defines provider/model credentials and model configuration. ACP Agent Profiles
[L209] instead use the external agent's model/authentication mechanism. Once a
[L210] conversation has started with one Agent Profile, the documentation says it cannot
[L211] simply be swapped to a different Agent Profile mid-conversation. [11]

[L213] Some capabilities are explicitly version/capability gated. For example, the
[L214] documented UI for allowing an OpenHands agent to switch among saved LLM
[L215] profiles appears when the connected Agent Server reports version 1.31.0 or later.
[L216] Secret scoping likewise depends on the backend advertising the relevant
[L217] capability, with enforcement occurring in Agent Server rather than as a merely
[L218] cosmetic Canvas filter. [11]

[L220] That is why the handoff never teaches “the button is always there.” The lesson
[L221] contract says to check the installed version/backend capability first.

[L223] Instructions, skills, tools, and permissions are different things
[L224] Current Canvas separates Customize from Settings. Customize contains areas
[L225] such as MCP Servers, Skills, Plugins, and Apps; Settings contains Agent, LLM,
[L226] Condenser, Verification, Application, and Secrets. These settings are scoped to the
[L227] active backend, so switching backends can mean looking at a different set of
[L228] saved skills, secrets, MCP servers, and capabilities. [12]

[L265] Self-hosted VM operation, boundaries, and recovery
[L266] The VM lesson intentionally does not invent hardware or compatibility facts that
[L267] the learner has not supplied.

[L269] Current official installation guidance supports Agent Canvas through direct/local
[L270] and Docker-based arrangements and documents VM/self-hosted backend
[L271] configurations. Persistent directories can be mounted outside a disposable
[L272] container so configuration and conversation-related data survive replacing the
[L273] image. [13]

[L276] facts:

[L289] with an explicit Unknown state for every uncertain value. It never requests an
[L290] API key, password, token, SSH credential, model-provider secret, or private

[L293] The VM can be trusted infrastructure without being a safe sandbox
[L294] The self-hosted documentation warns that a backend can execute commands and
[L295] reach files and networks made available to it, so the VM itself should be treated
[L296] as trusted infrastructure. Agent Canvas can also be paired with more isolated
[L297] execution arrangements rather than treating “running on a separate VM” as
[L298] synonymous with fine-grained sandboxing. [14]

[L300] This produces three different questions in the lesson:

[L302] Where does Canvas/backend software run?
[L303] Where does each conversation execute?
[L304] What files, networks, tools, and secrets can that execution environment
[L305] actually reach?

[L307] Those are deliberately not collapsed.

[L309] Remote iPad access is a networking and authentication question
[L310] OpenHands has current documentation specifically covering phone/tablet access.
[L311] It discusses approaches such as private network access and warns against
[L312] exposing a backend publicly without appropriate authentication. [15]

[L314] The learning site therefore treats the iPad as a client device, not as evidence that
[L315] the backend lives on the iPad. The learner is also warned that this is an attention-
[L316] intensive technical learning environment and is not intended for use while
[L317] driving.

[L319] Security controls need both policy and isolation
[L320] The SDK documents action-confirmation/security policies that can classify or gate
[L321] actions, including policies for always confirming, never confirming, or
[L322] confirming risky actions. Those mechanisms are useful controls, but the learning
[L323] content does not equate a confirmation dialog with operating-system isolation.
[16]

[L326] That distinction drives the practical rule taught in the site:
[L328] <PARSED TEXT FOR PAGE: 9 / 17>[L329]     Use approval and verification controls to govern decisions; use
[L330]     workspace/container/VM/network/permission boundaries to govern
[L331]     what is actually possible.

[L333] Failure diagnosis follows evidence, not guesswork
[L334] Current troubleshooting documentation separates several classes of symptom:
[L335] Canvas startup problems, backend connectivity problems, model/provider errors,
[L336] workspace-location mistakes, and extension/MCP problems. For example, a local-
[L337] model endpoint must be reachable from the backend, and a VM-backed
[L338] conversation sees the VM's accessible files rather than silently seeing files on the
[L339] learner's tablet or laptop. [17]

[L341] Maintainer issue evidence also shows why version labels matter. One 2026 SDK
[L342] issue documented an unreachable MCP server causing native OpenHands
[L343] conversation initialization to fail rather than degrade gracefully on the affected
[L344] released build. That is evidence for a real failure class and diagnostic exercise,
[L345] not justification for claiming every current OpenHands installation still has that
[L346] exact bug. [18]

[L31] ## What OpenHands is now

[L33] A major finding is that **“OpenHands” no longer means one monolithic application architecture**. Current documentation describes a multi-repository system, and older tutorials can describe a materially different generation. That distinction is essential to a learning environment because mixing old Local GUI/runtime instructions with current Agent Canvas/Agent Server instructions can produce incorrect deployment and troubleshooting guidance. citeturn14view1turn14view2

[L35] ### The active component model

[L37] The current browser-facing application is **Agent Canvas**. It is the browser client and control center for conversations, files, model configuration, backends, customization, and automations; it connects to one or more backends rather than itself being the execution sandbox. The current **Software Agent SDK** defines agent behavior, conversations, tools, workspaces, events, and related agent mechanisms. **Agent Server**, housed with the SDK, exposes that execution capability to clients through HTTP and WebSocket interfaces. **Automation Server** owns scheduled/event-driven work, while **Sandbox Server** is a separately maintained standalone control plane for sandboxed environments. citeturn14view1turn14view2

[L39] The current official component map is therefore best taught as:

[L41] | Layer | Plain-language responsibility | Important boundary |
[L42] |---|---|---|
[L43] | **Agent Canvas** | The control surface the person sees | It displays and directs work; it is not, by itself, the sandbox. |
[L44] | **Agent Server** | Runs and coordinates conversations, agents, tools, files, and workspace operations | This is a major enforcement and execution boundary. |
[L45] | **Software Agent SDK** | Defines how agents, conversations, tools, events, workspaces, model access, security mechanisms, and extensions behave | This is the principal code-level adaptation layer for agent execution behavior. |
[L46] | **Workspace / sandbox** | The place whose files and processes an agent can actually reach | This boundary determines the practical blast radius of agent actions. |
[L47] | **Automation Server** | Stores and dispatches scheduled or event-triggered agent work | It is separate from the interactive conversation lifecycle. |
[L48] | **Model/provider** | Supplies the model inference the agent uses for decisions | Hosting OpenHands does not automatically mean hosting the model. |

[L50] These boundaries are directly reflected in the official architecture documentation. A remote backend still presents the Agent Server API to Canvas, and Canvas can connect to a service on another machine or container. OpenHands Cloud and Enterprise add managed backend/control-plane arrangements around this model. citeturn14view2

[L52] ### Active, legacy, hosted, and commercial pieces

[L54] The current documentation explicitly marks the former Docker-based **Local GUI** as legacy/deprecated and directs active browser-client development toward Agent Canvas. The CLI remains SDK-powered and is described as feature-complete and primarily maintained for stability. The archived legacy repository preserves the previous backend/runtime design for historical use rather than defining the current system. citeturn14view1

[L56] OpenHands Cloud is the managed service. OpenHands Enterprise provides commercial self-hosting/managed-deployment features for organizations requiring those capabilities. Those are not interchangeable with the open-source single-user/local arrangements merely because they share OpenHands technology. citeturn14view1

[L58] Licensing likewise needs to be taught **per repository/component rather than as one blanket claim**. The current `OpenHands/OpenHands` and `OpenHands/software-agent-sdk` repositories carry MIT licenses, while the official component documentation instructs users to check each repository's own license. citeturn17view2turn17view3turn14view1

[L60] ### Self-hosting the application is not self-hosting the model

[L62] A self-hosted Agent Canvas/Agent Server arrangement can still send model requests to an external model provider. Current model configuration supports direct provider profiles, an OpenHands provider path, local OpenAI-compatible model endpoints, LiteLLM proxies, and ACP agents such as Claude Code, Codex, or Gemini CLI. A locally hosted model is a distinct architecture choice; for local model servers, the endpoint must be reachable from the **backend**, not merely from the learner's browser. citeturn18view1

[L64] That yields an important teaching distinction:

[L66] > **“OpenHands is on my VM” answers where the control/execution software runs. It does not, by itself, answer where model inference happens.**

[L68] The learning environment therefore tracks “application hosting” and “model arrangement” as separate VM-profile inputs instead of collapsing them into a single “self-hosted” checkbox.

[L70] ## From a submitted task to an inspectable result

[L72] The site handoff teaches OpenHands as a causal system rather than a collection of menus.

[L74] A useful ordinary-language trace is:

[L76] **Person → Canvas → selected backend/conversation → agent/model decision → permitted tool action → workspace or external service → observation/event → next decision → result and verification.**

[L78] Agent Canvas sends work to the active backend; the Agent Server owns conversation execution and streams observable events back to clients. Workspace choice determines which files and processes the agent can reach, while the model and agent profile determine the reasoning/model path and available agent configuration. citeturn14view2turn18view2

[L80] ### What actually changes at each step

[L82] When an OpenHands agent takes a step, the underlying SDK model is not simply “the AI writes code.” The agent reasons using an LLM, may choose a tool, receives the resulting observation, updates conversation state/events, and either continues or reaches a stopping condition. Tools can include terminal operations, file operations, connected MCP capabilities, and other configured components; those capabilities are constrained by the workspace and available tool catalog rather than by the agent's prose alone. citeturn14view2turn14view5

[L84] This matters for judging outcomes. An agent saying that something is finished is only a **claim**. Evidence can include changed files, command output, tests, tool observations, repository state, application behavior, or another task-appropriate verification result. The first activity in the prototype asks the learner to distinguish those concepts immediately rather than treating “agent says done” as completion.

[L86] ### Models and agent profiles are separate controls

[L88] Current Canvas distinguishes an **Agent Profile** from an **LLM Profile**. The Agent Profile controls which agent and agent-specific configuration a new conversation uses; an OpenHands Agent Profile can reference an LLM Profile, which separately defines provider/model credentials and model configuration. ACP Agent Profiles instead use the external agent's model/authentication mechanism. Once a conversation has started with one Agent Profile, the documentation says it cannot simply be swapped to a different Agent Profile mid-conversation. citeturn18view2

[L90] Some capabilities are explicitly **version/capability gated**. For example, the documented UI for allowing an OpenHands agent to switch among saved LLM profiles appears when the connected Agent Server reports version 1.31.0 or later. Secret scoping likewise depends on the backend advertising the relevant capability, with enforcement occurring in Agent Server rather than as a merely cosmetic Canvas filter. citeturn18view2

[L92] That is why the handoff never teaches “the button is always there.” The lesson contract says to check the installed version/backend capability first.

[L94] ### Instructions, skills, tools, and permissions are different things

[L96] Current Canvas separates **Customize** from **Settings**. Customize contains areas such as MCP Servers, Skills, Plugins, and Apps; Settings contains Agent, LLM, Condenser, Verification, Application, and Secrets. These settings are scoped to the active backend, so switching backends can mean looking at a different set of saved skills, secrets, MCP servers, and capabilities. citeturn18view0

[L98] This supports one of the site's most important adaptation lessons:

[L100] **An instruction can tell an agent what it should do; it does not magically give the agent the tool, secret, network path, file permission, or dependency required to do it.**

[L102] Accordingly, the adaptation workbench routes requests through progressively deeper layers:

[L104] | Desired change | First layer to investigate |
[L105] |---|---|
[L106] | “Always follow this project convention” | Repository guidance / skill |
[L107] | “Use this reusable procedure when relevant” | Skill |
[L108] | “Connect to a new external capability” | MCP or another supported integration |
[L109] | “Only this profile may access these capabilities” | Agent profile/tool/MCP/secret scope |
[L110] | “Change how the interface presents or controls work” | Agent Canvas |
[L111] | “Change conversation/tool/execution semantics” | SDK / Agent Server |
[L112] | “Change what the agent can actually access” | Workspace, sandbox, network, infrastructure |
[L113] | “Change unsupported core behavior permanently” | Maintained fork, after supported extension paths are ruled out |

[L115] This routing is presented as **decision guidance**, not an invented feasibility verdict.
